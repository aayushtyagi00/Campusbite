# CampusBite feature audit

19 November 2026 · Compared the original 27-section pilot brief with the local Next.js routes, components, server actions, Supabase migrations, Razorpay handlers, design exports and tests.

**Update after the audit.** The Current Vendors and onboarding work described below has since been implemented in the workspace. Admins can review applications at `/admin/applications` and publish participating shops from `/admin/vendors`. Applicants can return to `/vendor/onboarding` for drafts, corrections and decisions. The audit tables record the earlier baseline. Activation on a hosted installation requires the [onboarding migration](supabase/migrations/202611190002_vendor_onboarding.sql). [Setup instructions](README.md)

**The student ordering journey is the most complete part. The largest gap is getting a real stall from application to its first sale and then explaining where the money went.** An administrator can create a shop and assign its team. Publishing that shop requires linking it to one of three storefronts defined in code. Its owner can change existing prices and sold-out flags, but cannot build the menu, set opening hours or see a settlement statement.

### What “current vendors” means in this app

| Who is looking | What they see today | What the original workflows call for |
| --- | --- | --- |
| Student choosing a vendor | Home, `/court` and `/order-online` reuse the vendor-list component. Each stall already has its own `/stalls/{id}` page and each product its own detail page. Four courts can be selected. All three defined stalls belong to UniMall. | A court directory populated by approved shops, with trustworthy operating status and earliest pickup. Approving a new stall should give the campus a new listing without a code change. |
| Stall operator or owner | `/vendor` is the public application and sign-in landing page. After sign-in, the only workspace navigation item is **Shop dashboard**. `/vendor/board`, `/vendor/menu`, `/vendor/availability`, `/vendor/onboarding` and `/vendor/earnings` all redirect there. Owners also manage their team on that page. | A board staff can keep open during service, plus distinct owner tasks for menu, availability, onboarding and earnings. The existing protected actions and shop switcher can be reused. |
| Administrator managing participating shops | `/admin/vendors` redirects to applications. **Access Management** lists existing shops and memberships. **Commerce operations** separately maps a shop to a storefront and sets capacity. | A **Current Vendors** directory that opens a shop record with its review decision, storefront, location, payment readiness, menu/hours readiness, team and ordering status together. Keep incoming applications accessible separately. |

The directory and page groupings above are a proposed interpretation of the workflows. The brief specifies what each role must accomplish and leaves exact URLs open. Compare the [vendor design](design/vendor.png), [vendor router](src/app/vendor/%5B%5B...screen%5D%5D/page.tsx), [admin router](src/app/admin/%5B%5B...screen%5D%5D/page.tsx) and [public catalog screens](src/components/student.tsx).

**Suggested navigation for the update.** Give an administrator **Applications → Review application** and **Current Vendors → Shop detail**. Give an approved vendor **Order board → Order detail**, **Menu → Item editor**, **Availability**, **Onboarding & shop settings**, and **Earnings → Settlements**. Keep team management available to the owner. Staff fulfilling orders should land on the selected stall’s board. Students can continue through **Choose a court → Choose a stall → Menu → Product** using the existing screens once the catalog reads from those same shop records.

## 1. Planned features already implemented

| Area | What the application does today |
| --- | --- |
| Public discovery and menus | Responsive mobile and desktop navigation, a persistent court picker, stall/dish search and category filters. Stall and product pages show location, hours, prices, dietary labels, descriptions, available photos and sold-out controls. Some descriptions include allergens. The directory estimates an earliest pickup. [Catalog screens](src/components/student.tsx) |
| Student sign-in | Supabase Google and email/password flows, email signup confirmation, sign-out, a checkout return path and emailed recovery-code verification before changing the password. The browser retains the cart across navigation and sign-in. Real email delivery and provider settings depend on the environment. [Student auth actions](src/lib/student-auth-actions.ts) |
| Bag and checkout | One vendor per cart, replace-cart confirmation, persistent quantities, price-change acknowledgement, preparation note, subtotal, total and pre-acceptance cancellation terms. The server rechecks prices, sold-out state, vendor and an eight-item maximum. [Checkout screen](src/components/student-flow.tsx) and [checkout actions](src/lib/commerce-actions.ts) |
| Scheduling and reservations | Ten-minute pickup windows in campus time, up to an hour ahead, using opening hours, quantity-sensitive preparation and timing allowances. The database serializes capacity reservations, limits simultaneous unpaid holds per student, reuses a matching checkout request and expires holds. Admins can set capacity per storefront. [Scheduling](src/lib/campus.ts) and [reservation transaction](supabase/migrations/202611180002_commerce.sql) |
| Payments and paid-order admission | Razorpay Checkout integration, server-persisted order intent, provider receipt lookup following a failed create call, signed callback and webhook processing, amount/currency checks and duplicate-capture protection for the same payment. A verified, timely capture creates a vendor queue entry and a 90-second acceptance deadline. [Razorpay integration](src/lib/razorpay.ts) and [webhook](src/app/api/payments/razorpay/route.ts) |
| Fulfillment and collection | Assigned staff can accept, reject, start preparation, mark ready and verify pickup. SQL enforces deadlines, valid transitions and single collection. A six-digit code appears to the student when ready. The server checks the code against that order and limits repeated wrong attempts per order. [Vendor controls](src/components/vendor-order-controls.tsx) and [fulfillment transaction](supabase/migrations/202611180002_commerce.sql) |
| Tracking, cancellation and refunds | My Orders retrieves a student's stored orders with purchased item and price snapshots, pickup location, window, countdown, activity, payment/refund status and amount. Active details poll while visible. A student can cancel while awaiting acceptance. Rejection, acceptance timeout and late capture can initiate full refunds. The job endpoint submits or recovers refunds and records provider-confirmed outcomes. [Order screens](src/components/student-flow.tsx) and [commerce job](src/app/api/jobs/commerce/route.ts) |
| Vendor applications and access | A public form collects contact and stall details. Admins review applications, create shops and grant or revoke access. Owners can manage staff and managers within their shop. Multi-shop operators can switch shops. Server checks, database row-level security and access-change audit records underpin these actions. [Staff actions](src/lib/staff/actions.ts) and [team migration](supabase/migrations/202611190001_shop_owner_team.sql) |
| Vendor and admin operations | Vendors see active and recent orders, quantities, notes and pickup time. Owners and managers can edit existing menu prices and sold-out flags and see recent sales recorded at collection. Admins can enable a mapped storefront, set capacity and read recent orders, refund status and student support notes. [Shop dashboard](src/components/staff-vendor.tsx), [menu editor](src/components/vendor-menu.tsx) and [admin orders](src/components/recent-commerce-orders.tsx) |
| Platform and help | One Next.js/TypeScript application serves three audiences, with Supabase/PostgreSQL persistence, integer paise, timestamped fulfillment events, shop-scoped access and indexed order queries. The student PWA has a manifest, icons and an offline fallback. Public support, privacy, terms and pickup/refund guidance exist. [Database migration](supabase/migrations/202611180002_commerce.sql), [service worker](public/sw.js) and [help pages](src/components/student-help.tsx) |

## 2. Planned features still pending or incomplete

| Area | Gap against the pilot brief |
| --- | --- |
| **Vendor onboarding and approval** | The stored application moves from **Submitted** to **Reviewed**. Build resumable drafts, under-review status, explicit approval, requested corrections and resubmission, rejection and suspension. Collect verified owner contact, structured court/cuisine/hours, applicable registration documents and agreement acceptance. Track provider onboarding and account reference. Publish only when approval, payments, menu, hours and the accepting-orders switch are ready. |
| **Current Vendors and public catalog** | Add an admin directory and per-shop detail view. Put courts, stall identity, photos, hours and location into editable records linked to the application and operating shop. Live mode overlays database prices, menu items, capacity and enablement on a hard-coded stall list. A newly created fourth shop cannot acquire its own public listing through the existing UI. The three illustrative UniMall stalls meet the proposed pilot count only as catalog entries. |
| **Vendor order board** | Build the dedicated board with queues for awaiting acceptance, accepted/scheduled, preparing, ready and completed. Today's list has actions and polling. It lacks vendor-side countdowns, recommended prep-start times, the full pickup interval on the card, rejection reasons and an order detail view. Add authorized Realtime updates, reconnect refresh, connection status, manual refresh and opt-in sound with a test button. |
| **Menu and availability pages** | Allow authorized vendors to create, edit and archive items, manage categories and descriptions, upload photos, maintain dietary/allergen details and prep times, and optionally track units in stock. Add open/close, pause/resume, weekly hours, date exceptions, last pickup, capacity, basket limits, acceptance allowance, safety buffer and advance horizon. Today the two editable product fields are price and sold out. Enablement and capacity belong to the admin UI. |
| **Accurate pickup offers and stock holds** | Checkout calculates choices without global live slot usage. A student can select a full window and learn that only when reserving. Load actual remaining capacity before presenting windows and keep the database check for competing checkouts. Add atomic stock holds and release where stock is tracked. Current holds can last up to five minutes, shortened by prep time. The brief proposed two minutes for testing. Late captures currently go straight to refund. The brief calls for rechecking whether the original slot can still be fulfilled. |
| **Student identity, recovery and account** | Add name/profile management and notification preferences. The reset screen supports email OTP. The reset link lacks a recovery-confirmation handler, and password confirmation, recovery result, resend countdown and Google-user guidance are missing. Implement shared student recovery counters, cooldown and five-failure lock, campus-IP-aware challenges and abuse monitoring. Staff throttles already exist. Verify provider-level protections, direct email delivery, identity linking and expired/reused credentials with the configured project. |
| **Payment progress and recovery** | Provide distinct failed, pending-verification and successful outcomes. The app shows pending or verified, and the checkout callback opens My Orders even when verification returns an error. Store individual payment attempts and incoming webhook event IDs/results, retry processing durably, recover aged pending payments, and handle extra captures and out-of-order events with an operator-visible resolution. Current order details and pickup tickets are states inside `/orders`. Individual order URLs redirect to the list. |
| **Pickup and uncollected orders** | The code is generated at Ready. The brief calls for generating it after acceptance and allowing collection only at Ready. Add protected code storage, per-operator attempt limits and the collecting staff identity alongside the event time. Add uncollected status, holding deadlines and a vendor no-show procedure. |
| **Refunds, support and investigation** | A student can leave one support note. The admin screen reads the latest 50 orders. Add lookup by order reference, a full investigation timeline, provider references, case ownership/status, resolution notes, linked adjustments/refunds, manual refund decisions, failed/overdue refund alerts and cases for problems after acceptance or collection. The existing admin refunds URL redirects to Overview. |
| **Earnings, fees and reconciliation** | Recent collected sales are the only vendor financial view. Build per-order food value, applicable taxes and fees, commission, provider charges, refunds, adjustments and vendor payable. Snapshot the financial policy. Add append-only entries, transfer/settlement records and allocations, vendor statements for pending/settled amounts, and an admin reconciliation queue for unmatched payments, refunds and settlements. Finance and settings URLs redirect to Overview. Basic reconciliation belongs in the pilot. Automated payout release was deferred. |
| **Notifications and background operations** | Ship web-push subscriptions/preferences, student status and refund notifications, vendor new-order/deadline alerts, and admin exception alerts. The current endpoint expires unpaid/unaccepted orders and processes due refunds. Other planned work includes payment recovery, notification delivery, reconciliation and no-show checks, with job attempts, errors, leases and monitoring. Scheduling the endpoint is an external deployment step. |
| **Deployment, security and pilot evidence** | Verify deployment-specific OAuth/email settings, production sender, admin MFA, private document storage and validated uploads, student login/checkout abuse controls, platform-wide pause, monitoring, backups/restore and rollback. The repo includes local tests and a staging reservation-load script. It does not establish class-break capacity, two-device fulfillment, real provider refunds, production reconciliation or a completed pilot. Run the end-to-end scenarios and measure readiness, waits, misses, complaints and discrepancies. |
| **Business decisions and operations** | Confirm participating vendors and campus arrangements, provider eligibility and marketplace transfers, tax/fee treatment, refund-charge ownership, cancellation after acceptance, revised pickup times, no-shows, complaint remedies, support hours and vendor agreements. Store the policy applied to each order. Existing public terms cover basic pickup and pre-acceptance cancellation. Campus agreements, vendor training and supervised pilot results require operational evidence outside the source tree. |

**Original post-pilot scope.** Additional login and payment providers, advanced search and favorites, configurable extras/combos/variants, advanced scheduling, batch preparation, advanced exports, SMS/WhatsApp and native apps were intentionally deferred. These do not count as unfinished pilot commitments.

### Architecture and verification notes

The student, vendor and admin catch-all routes dispatch to separate views. A single route file can serve many screens. The vendor issue comes from its explicit redirects and one-item navigation. On the data side, payment references, reservation expiry, fulfillment, refund status, support text and events mostly share one commerce-order row. Separate vendor order and sale records support the stall. This explains how pickup can work while investigations, multiple attempts and settlement matching remain incomplete. The ten HTML/PNG design exports are references for UI behavior. [Design handoff](design/README.md)

The local configuration selects live mode and has Supabase settings. The Razorpay key ID, key secret, webhook secret and commerce job secret are unset in the local environment examined. The checkout action explicitly requires all four. A real charge, refund or settlement and production service configuration were outside this local verification. [Checkout requirements](src/lib/commerce-actions.ts) and [setup instructions](README.md)

**Checks run for this audit.** TypeScript passed. Both local database test groups passed, covering 11 individual scenarios. All 10 Playwright tests passed against the existing local production build using preview data and local provider fixtures. They cover mobile/desktop discovery, cart behavior, portal entry, offline fallback, checkout return routing and admin access management. The staging load script writes reservations to a designated staging database and was outside this local review.
