# CampusBite pilot implementation audit

## Built for the release branch

| Workflow | What can be tested |
| --- | --- |
| Student ordering and public catalog | Verified, approved vendor storefronts, persistent bag, server-priced checkout, sign-in, recovery, order history and pickup tracking. Court names now come from database records for discovery and onboarding. |
| Pickup availability | Regular and weekday shifts can cross midnight IST. Vendors can set advance booking, capacity, prep buffer, acceptance deadline, last-pickup cutoff and holding time. Checkout explains a closure, full slots or insufficient preparation time. |
| Payments and recovery | Signed deliveries enter a durable queue. The worker looks up outstanding gateway orders after browser closure, records attempts and retries verification. The payment journal records captures and verified refunds. Extra captures have separate entries and a dashboard refund procedure. |
| Handoff | The ordering student receives a six-digit code after acceptance. Collection requires Ready status, an authorized operator and a matching code. Per-order and per-operator limits restrict failed submissions. An optional holding time marks missed pickups uncollected. |
| Vendor and admin operations | Vendor board, stock, earnings, admin order search, case owner, student-visible reply, full refund decision, global ordering pause, payment issues and worker run status. |
| Alerts and access | Opt-in Web Push with delivery retries and deadline reminders. Student preferences govern order and refund alerts. Admin authenticator enrollment and database enforcement are implemented. |
| Verification | The PostgreSQL tests exercise migrations, access control, overnight windows, existing ready codes, no-shows, idempotent capture, and reservation through collection. The browser suite uses local provider fixtures. See the README for deployment and incident steps. |

## Outstanding before a public pilot

| Item | What completes it |
| --- | --- |
| Vendor settlement | Owner confirms commission, who pays fees, tax treatment and Route eligibility. Then implement and reconcile vendor transfers, adjustments, settlement allocations and payable statements. |
| Hosted order rehearsal | Apply the migrations to a dedicated test database and configure the test deployment, scheduler, provider webhook, and VAPID keys. Verify one complete pickup and one refund in the Razorpay dashboard with separate student and vendor devices. |
| Hosting and identity | Check HTTPS redirects, email delivery, CAPTCHA, admin authenticator recovery, notification delivery, worker cadence, monitoring and restore on the target deployment. |
| Reliability and pilot results | Run a class-break traffic rehearsal and supervised pilot with participating vendors. Measure readiness against the promised window, duplicate handoffs, customer wait from arrival to collection, complaints and unmatched payments. |
| Business operations | Campus and vendor arrangements, tax/invoice rules, support hours, budget, field training, actual refund processing and bank reconciliation require the operator and the providers. |

## Historical comparison before this release

22 November 2026 · Compared the supplied 27-section plan with the current local application, SQL migrations, provider handlers, and tests on `feature/vendor-onboarding`.

**The student can browse, reserve a pickup, and track an order. The vendor can onboard, publish a menu, and fulfill a verified paid order. The biggest unfinished pilot requirement is tracing that payment through fees, refunds, and the vendor’s bank settlement.** Razorpay checkout and refunds have application code. This audit did not establish that a payment or settlement succeeded on the hosted installation.

## 2. What is incomplete and what to do next

| Area | Current gap | Work required for the pilot |
| --- | --- | --- |
| **Payment recovery and webhook processing** (§§13–15, 20) | The webhook processes events inline. An order holds one provider payment reference. A second, different capture has no resolution workflow. Checkout opens My Orders even if callback verification reports a problem. | Persist payment attempts and incoming provider event IDs/results, retry failures, recover aged pending payments, and resolve extra captures. Give the student distinct failed, pending-verification, and confirmed outcomes. Verify recovery after the browser closes or the provider response is lost. |
| **Vendor settlements and admin reconciliation** (§§3, 12–14, 19) | The earnings screen reports customer payments before fees and settlement. Admin Finance redirects to Overview. The app cannot explain how much a vendor should receive or match it to a bank settlement. | Agree fees and tax treatment. Show all applicable charges at checkout and snapshot the policy per order. Build financial entries, adjustments, vendor payables, transfer/settlement references and allocations, vendor statements, and an admin view for unmatched amounts. Confirm the provider arrangement. Automated payout release can follow the pilot. |
| **Admin investigation, refunds and complaints** (§§18–19, 22, 25) | Admins see the latest 50 orders and one student note per order. There is no lookup across historical orders, case lifecycle, or dedicated refund decision screen. | Build order-reference search with customer/vendor details, activity, and provider payment/refund references. Add assigned cases, resolution notes, linked refunds/adjustments, failed or overdue refund alerts, and a remedy when an accepted order cannot be fulfilled. |
| **Pickup protection and no-shows** (§§3, 13, 17–18, 20) | The code is generated at Ready and stored as text. Wrong attempts are limited per order. Collection records the time but lacks the collecting operator’s identity. No uncollected state or holding deadline was found. | Generate the protected code after acceptance, display it only to the ordering student, and keep verification restricted to Ready. Add per-operator limits, record who handed it over, and implement the agreed holding period and uncollected process. |
| **Scheduling differences and court discovery** (§§3, 8, 10–12) | The checkout hold lasts up to five minutes, compared with the proposed two. Acceptance is fixed at 90 seconds, the advance horizon at 60 minutes, and the safety buffer is fixed. Closing time bounds pickups. Court names are defined in code, and directory cards estimate earliest pickup before checkout checks shared capacity. | Test the hold duration with the payment flow. Expose the required per-vendor timing controls and separate last-pickup cutoff. Use shared availability for the directory’s earliest pickup and persist court records for expansion. |
| **Push, jobs and operational alerts** (§§4, 16, 20, 23) | Students get updates while My Orders is open. Vendors have board sound and a visible countdown. The worker handles expiry and refunds, but there is no push subscription/delivery flow, general job history, or admin exception alerting. | Add web push for students and vendors, approaching-deadline reminders, retryable delivery and recovery jobs, job ownership/leases, attempt history, last error and failure alerts. Configure and observe the scheduler in the target environment. |
| **Production auth, security and service setup** (§§5–7, 14, 21, 25) | Callback, email, challenge, and provider settings depend on the deployment. The reviewed local environment file selects live mode but has no Razorpay credentials, webhook secret, commerce-job secret, or Turnstile keys set. Production values were not inspected. | Configure and test target-environment migrations, HTTPS, OAuth redirects and same-email linking, SMTP delivery, CAPTCHA on shared campus Wi-Fi, direct Supabase recovery limits, admin MFA, and student login/checkout abuse controls. Verify Razorpay webhooks and a controlled refund end to end. |
| **Reliability and release operations** (§§23–25) | Local scripts cover selected flows. The load harness exercises database reservations only. Per-shop pause exists. No evidence was found of a tested global pause, production monitoring, restore rehearsal, rollback drill, or complete incident instructions. | Test the last slot and stock unit under concurrent checkout, acceptance/cancellation and simultaneous pickup races, provider failures/replays, worker restart, separate student and vendor devices, and full class-break traffic. Set up monitoring, test global pause and restore/rollback, and document incident response. |
| **Business rules and supervised pilot** (§§1–3, 23, 26–27) | The repo has student terms, privacy and refund guidance, sample stalls, and vendor agreement acceptance. These do not establish the campus agreement, confirmed vendors, fee model, or field results. | Confirm one court and 3–5 vendors, campus/provider arrangements, food-business requirements, tax and invoicing, budget, refund-charge ownership, cancellation after acceptance, revised pickup times, complaints, support contact and hours. Train vendors, rehearse payments/refunds, and run a supervised class break. Measure overselling, duplicate handoffs, privacy, money traceability, acceptance/readiness, counter waits, missed orders and repeat use. |

**Pilot acceptance criteria.** The plan calls for every payment and refund to be traceable, zero oversold windows, duplicate fulfillments or cross-vendor access, at least 90% of accepted orders ready within the promised window, and a median collection wait below two minutes. The workspace contains no measured pilot result for these targets.

**Post-pilot scope.** The plan defers extra login/payment providers, advanced search and favorites, configurable extras/combos/variants, advanced scheduling, batch preparation, advanced exports, SMS/WhatsApp, and native apps. Basic settlement reconciliation and web push are in the pilot scope.
